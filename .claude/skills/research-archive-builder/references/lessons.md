# 교훈: 사용자가 실제로 고쳐 달라고 한 것들

첫 실전(정인용 사이트)에서 받은 피드백을 시간 순으로 정리하고, 각각을 다음 작업의 규칙으로 바꿨다. 사용자의 말은 거의 그대로 옮겼다.

## 1. 디자인

| 사용자 피드백 | 원인 | 규칙 |
|---|---|---|
| "디자인이 너무 별로입니다" (첫 결과: 파란 강조, 둥근 카드, 그림자, 이모지) | AI 기본 미감(1차 디폴트) | 시작부터 `avoid-ai-design`, `antislop-ui` 규칙 적용. 스캐너(`.claude/skills/avoid-ai-design/scripts/detect.mjs`)로 P0/P1 확인 |
| "스킬들 총동원해서 진짜 그럴싸하게" | 방향 없이 금지만 하면 밋밋한 '무균 디폴트'가 됨 | 주제에서 방향을 끌어낸다(연구자의 세계: 검사 결과지, 측정, 신뢰구간). design-pick으로 팩 2~3개를 미리보기와 함께 사용자가 고르게 한다. 정인용은 '아카이브 도록(web-atelier-archive-serif)'을 골랐다 |
| (팩 적용 시) | 팩 명세에 2차 디폴트(크림 바탕, 대문자 고정폭 라벨, 가운뎃점 캡션)가 섞여 있음 | 팩의 구조는 가져오되 avoid-ai-design의 SD 목록과 충돌하는 부분은 바꾸고, 바꾼 이유를 DESIGN.md에 적는다 |
| 시그니처 | | 사이트 전체에 하나: 측정값 눈금(`.gauge`). 빨강은 측정값에만 쓴다 |

## 2. 구성과 정체성

| 피드백 | 규칙 |
|---|---|
| "내 연구자 정체성을 보여줄 수 있게 디자인하고 구성" | 연대기 목록이 아니라 **연구 질문**을 축으로 묶는다. 홈 머리말은 핵심 질문 한 문장. 도록 색인은 질문별/주제별 두 보기 |
| "각 논문의 결론 부분이 더 부각되면 좋겠음" | 모든 글 머리에 결론 블록(`.concl`). 결론 문장은 논문 Conclusion 절을 직접 읽고 쓴다(에이전트 요약을 믿지 않는다) |
| "다른 정보와도 제대로 연결" | 글 끝에 같은 질문, 같은 주제 연구(`.connect`). 해설 본문에서도 관련 글을 '함께 읽기'로 한 번 연결 |
| "(글쓴이 카드) 어차피 내가 쓰는거니 이런건 필요 없어" | 글쓴이 카드 없음. 저자 역할은 결론 블록 아래 한 줄 |
| PTE 논문의 핵심은 "암묵지의 표준화" | 사용자가 짚은 핵심을 본문 섹션과 결론, 도록 짧은 제목에 반영. 단 논문이 검증하지 않은 부분은 '다음 질문'으로. 사용자: "과장 없이 하면 되요" |

## 3. 인터랙션

| 피드백 | 규칙 |
|---|---|
| 처음: "독자랑 상호작용도 하고" | 글마다 3~5개의 실제 수치 기반 인터랙티브 요소 + 퀴즈 |
| "좀 더 인터렉티브할 수 없을까?" → 숫자 짐작 장치, 한 눈금 그림을 만들었더니 "이게 뭔지 직관적이지 않아" | 숫자 맞히기 같은 장치는 연구 이해에 도움이 안 된다 |
| "이런 짐작보다는 연구의 필요성을 공감시키는게 좋아보이는데" | **이런 상황이라면?** 카드(`.scene`): 연구가 출발한 현장 장면, 선택지 2~3개, 고르면 '왜 이 연구가 필요했나'가 펼쳐짐. 정답 없음. 글 머리와 홈 상단 |
| 브라우저에만 저장되는 투표, 반응 버튼, 미연결 댓글 | 아무에게도 전달되지 않는 상호작용은 넣지 않는다 |

## 4. 내용과 목소리

| 피드백 | 규칙 |
|---|---|
| "내 얼굴에 침뱉기는 하지 맙시다" | 저자 사이트에서 저자 논문의 오류, 불일치, 오타를 지적하지 않는다. 해설자의 회의적 해석("0.54는 높지 않다", "우연 수준과 비슷", "검정되지 않았다")도 금지. 표 값으로 조용히 통일하고, 발견한 불일치는 **채팅에서 사용자에게만** 알린다 |
| 저자 역할 오류(대사증후군 논문은 공동 1저자인데 공저자로 표기) | PDF의 동등 기여 표기만 보면 놓친다. 사용자가 준 분류를 1순위로 대조 |
| "프리프린트는 저널 심사 중이고 많이 변할거니 빼고" | 기본은 제외 |
| 나중에 "프리프린트도 넣되 under review 강조" → "너무 강렬해, 상세 페이지에서만" | 해설 글: 머리, 결과 직전, 꼬리에 경고 상자. 홈 색인과 목록: 표시 없음, 상세에 한 줄. 목록에서는 게재 논문 뒤로 |
| 문체 | 존댓말, 짧은 문단, 비유. 전문 용어는 툴팁(`.term`) |

## 5. 운영 (에이전트, git, 도구)

- **에이전트끼리 파일 충돌**: 공용 scratchpad에 `pdftotext` 결과를 같은 이름으로 써서 다른 논문 내용이 섞인 적이 있다. 에이전트마다 하위 폴더를 지정한다.
- **공유 자산을 작업 중에 바꾸면** 에이전트가 혼란스러워한다. 토큰 이름은 바꾸지 말고 값만 바꾼다. 글은 토큰만 쓰게 해 두면 자동으로 따라온다.
- **에이전트가 논문에 없는 숫자를 만든다**: 계열 평균, 우연 기준선, 다수 클래스 비율. 프롬프트에서 금지하고, 받은 뒤 grep으로 확인한다(`scripts/voice_check.py`).
- **에이전트 보고서의 '논문 불일치' 목록**은 사용자에게 알릴 가치가 있지만 페이지에는 절대 들어가면 안 된다.
- **전역 변수 충돌**: 데이터 파일은 `window.CATALOG` 한 이름으로만 노출(IIFE로 감쌈). 글마다 자체 스크립트가 `const P` 같은 이름을 쓴다.
- **Stop hook이 커밋을 요구**한다. 완성되고 검수된 파일부터 하나씩 커밋. 에이전트가 쓰는 중인 파일은 커밋하지 않고 이유를 말한다.
- **모바일 버그 패턴**: 좁은 화면에서 상세 패널을 색인 안으로 옮기는 구조라, 색인을 다시 그리기 전에 패널을 원위치시켜야 한다.
- **네트워크**: 이 환경에서 jsdelivr 폰트 요청은 막혀 있다(실제 사이트에서는 정상). Crossref 조회도 막힐 수 있어 DOI가 PDF에 없으면 링크를 빼고 사용자에게 알린다.
- **Playwright**: `/opt/pw-browsers/chromium` 사용, `npm i playwright@1`은 scratchpad에 한 번. `playwright install` 금지.
- **PDF 읽기**: 20쪽 넘으면 `pages` 나눠 읽기. 숫자는 `pdftotext -layout`로 대조.

## 6. 진행 방식

- 사용자는 중간에 새 PDF를 계속 보낸다. 받자마자 첫 쪽으로 식별하고 중복을 확인한 뒤, 기존 작업과 충돌하지 않게 병렬로 진행한다.
- 진행이 길어지면 짧게 상황을 알린다. 작업 목록(TaskCreate)으로 큰 단계를 관리한다.
- 취향이 갈리는 결정(디자인 팩, 첫 화면 구성)은 AskUserQuestion으로 미리보기와 함께 묻는다. 나머지는 합리적 기본값으로 진행하고 나중에 알린다.
