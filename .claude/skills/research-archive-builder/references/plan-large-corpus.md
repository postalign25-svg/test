# 계획: 논문이 많고, 연구 철학을 직접 추론해야 하는 경우

대상 예: 교수님 한 분의 논문 전체(수십~수백 편). 첫 실전과 다른 점은 세 가지다.

| | 첫 실전(정인용) | 이번(교수님) |
|---|---|---|
| 초점 | 사람 + 논문 | **논문 위주** (이력, 수상은 최소) |
| 연구 철학 | 사용자가 긴 소개글로 줌 | **Claude가 모든 논문을 읽고 추론** |
| 규모 | 23편, 전부 해설 | **훨씬 많음** → 등급제 필수 |

교수님 논문에서 교수님의 자리는 대개 **교신저자**다. 역할 분류에 교신저자를 넣고, 연구실의 흐름(어떤 학생, 어떤 공동연구 기관과 무엇을 해 왔는지)이 드러나게 한다.

---

## 0단계. 받기와 분류 (사람 1회 확인)

1. **PDF 받는 방법을 먼저 정한다.** 채팅 업로드는 한 번에 몇 편씩이라 느리다. 권장 순서:
   - (가장 좋음) 사용자가 PDF를 저장소의 `papers/` 폴더나 별도 비공개 저장소에 올리고 알려 준다. `papers/`는 `.gitignore`에 넣어 **공개 사이트에 PDF가 올라가지 않게** 한다(저작권).
   - 또는 zip 하나를 업로드.
   - 함께 받으면 좋은 것: 논문 목록(CV, Google Scholar, ORCID), 교수님이 공개를 원치 않는 논문, 강조하고 싶은 논문, 연구실 이름.
2. `scripts/pdf_triage.sh <폴더>`로 모든 PDF의 첫 쪽을 읽어 `work/inventory.tsv`를 만든다: 파일, 제목 추정, 학술지, 연도, DOI, 쪽수, 첫 저자, 교수님 이름 위치. `cmp`/해시로 중복을 표시한다.
3. 분류: 원저, 종설, 프리프린트, 학회 초록, 단행본 장, 정정(erratum). **프리프린트는 기본 제외**(사용자가 원하면 경고와 함께).
4. **체크포인트 A**: 인벤토리 표를 사용자에게 보여 주고 빠진 논문, 뺄 논문, 역할 오류를 확인받는다.

### 작업물 보존 (컨테이너는 세션이 끝나면 사라진다)

- 카드(`work/cards/`)와 철학 초안은 몇 시간짜리 작업의 결과다. **완성될 때마다 커밋**해야 다음 세션에서 이어 갈 수 있다.
- 다만 카드에는 원문 인용과 '논문 불일치' 메모가 들어 있어 공개되면 안 된다. 선택지:
  1. 사이트 저장소가 공개라면, 작업물은 **배포하지 않는 브랜치**(예: `work`)에 커밋한다. GitHub Pages는 지정한 브랜치만 배포한다. 단 공개 저장소의 다른 브랜치도 GitHub에서 보이므로, 민감하면 2번.
  2. 비공개 저장소를 하나 더 만들어 `papers/`와 `work/`를 거기에 둔다(가장 안전).
- PDF 자체는 어디에도 공개 커밋하지 않는다(`.gitignore`에 `papers/`).

## 1단계. 논문 카드 (모든 논문, 끝까지 읽기)

- 카드 형식: `references/data-schema.md`의 `PaperCard`. 한 편당 JSON 하나, `work/cards/<id>.json`.
- **근거 인용 필수**: 결론, 주요 수치, 한계는 원문 짧은 인용 + 쪽 번호. 철학 추론의 증거가 된다.
- 에이전트 배분: 1명당 5~8편(짧은 논문은 더 많이). 프롬프트는 `agent-prompts.md`의 '논문 카드' 템플릿. 각자 `work/tmp/<agent>/`만 쓴다.
- 규모가 크면 Workflow 도구가 맞지만, **사용자가 명시적으로 허락해야 쓸 수 있다**("workflow 써도 돼", "ultracode" 등). 기본 크기 가이드는 에이전트 10명 미만이므로, 100편 이상이면 사용자에게 크기를 늘려도 되는지 묻는다. 허락이 없으면 Agent 도구로 8~10명씩 나눠 여러 번 돌린다.
- **카드 검증**: 무작위 10%를 다른 에이전트가 PDF와 대조(수치, 역할, 결론). 오류율이 높으면 그 배치를 다시.
- 카드에서 바로 쓸 것: 연도, 학술지, 역할, 연구 설계, 데이터 출처, 질환/영역, 방법 계열, 외부 검증 여부, 핵심 수치, 결론.

## 2단계. 연구 철학 추론 (가장 중요, 가장 조심)

목표: 교수님이 직접 쓴 소개글 없이도 "이 연구실은 무엇을 묻는가"를 **근거와 함께** 보여 주기.

1. **기술 통계 지도**(해석 없이): 연도별 편수, 주제 분포, 방법 계열 변화, 데이터 유형, 외부 검증/전향 연구 비율, 자주 함께한 기관과 저자, 학술지 분야. → 사이트의 '한눈에 보기'와 철학 추론의 바탕.
2. **주제 묶기**: 카드 요약만 모아(전문 말고) 에이전트 1명이 4~7개 주제로 묶는다. 각 주제에 속한 논문 id 목록과 묶은 이유.
3. **반복되는 질문과 태도 찾기**: Discussion/Conclusion에서 반복되는 문장 패턴을 찾는다. 예: "외부 검증이 필요", "해석 가능성", "임상 흐름에 넣기", "데이터가 적은 병원", "라벨의 질". 이것이 철학의 원재료다.
4. **철학 초안**: 3~5개의 연구 질문(정인용 사이트의 QUESTIONS 형식)과 한 문장 핵심 질문. 각 주장마다
   - 근거 논문 **2편 이상**(id, 인용, 쪽),
   - 확신도(높음/중간/낮음),
   - 교수님 논문에 실제로 나온 표현을 최대한 그대로.
5. **반대 검증**: 다른 에이전트에게 "각 주장에 반하는 논문, 빠진 큰 흐름"을 찾게 한다. 결과를 반영.
6. **체크포인트 B (필수)**: `work/philosophy-draft.md`를 사용자에게 보여 주고 확인받는다. 사람의 신념을 대신 말하는 일이므로, 확인 전에는 사이트에 '철학'이라는 이름으로 확정해 넣지 않는다. 확인 전 표현은 "논문들이 반복해서 묻는 것".

금지: 논문에 근거가 없는 인생관, 성격, 동기를 지어내기. "환자를 위하는 따뜻한 마음" 같은 상투적 문장.

## 3단계. 등급 나누기

| 등급 | 대상 | 산출물 |
|---|---|---|
| A. 해설 글 | 질문마다 대표 2~3편, 교신/제1저자 우선, 연구실을 대표하는 데이터나 방법, 사용자가 강조한 논문. 보통 10~20편 | `posts/<slug>.html` 인터랙티브 해설(첫 실전과 같은 수준) |
| B. 논문 페이지 | 나머지 원저 전부 | **카드 데이터로 자동 생성되는 공통 페이지** `paper.html?id=<id>`: 상황 카드, 결론, 핵심 수치 눈금, 요약, 원문 링크, 같은 질문/주제 연결. 개별 HTML을 쓰지 않는다 |
| C. 목록만 | 학회 초록, 정정, 짧은 서신 | 논문 목록에만 |

B 등급의 공통 페이지는 새로 만들어야 한다(첫 실전에는 없었다). `assets/site.js`의 scene/concl/connect 부품을 재사용하면 된다.

**체크포인트 C**: A 등급 목록을 사용자에게 확인받는다.

## 4단계. 디자인

- 새 사이트면 주제에서 방향을 끌어낸다(교수님 분야의 사물, 문서, 도구). 첫 실전의 '검사 결과지 + 측정값 눈금'을 그대로 재사용하지 말고, 맞는지 먼저 판단한다.
- design-pick으로 팩 2~3개를 미리보기와 함께 제시. '논문 위주'라면 도록(아카이브), 정밀 그리드, 신문형 다단 등이 후보.
- 첫 화면은 보통 "연구 질문 중심"이 정체성을 가장 잘 드러냈다. 질문별/주제별/연도별 보기 전환.
- 논문이 많으므로 홈에 필요한 것: 검색, 필터(주제, 연도, 역할, 방법), 연구 흐름 타임라인(연도 × 주제). 차트는 dataviz 스킬을 먼저 읽는다.

## 5단계. 해설 글(A 등급)과 통합

- 에이전트 1명 = 논문 1편, `agent-prompts.md`의 '해설 글' 템플릿 그대로. 이미 만든 카드를 함께 넘겨 다시 읽는 비용을 줄인다(그래도 PDF 전체 읽기는 필수).
- 동시 실행은 10명 안팎. 완성되는 대로 검수 → catalog 추가 → 커밋.
- 카드 → catalog.js 변환은 손으로 하지 말고 스크립트로(`work/build_catalog.py`를 이 단계에서 작성). 수백 편을 손으로 넣으면 실수가 난다.

## 6단계. 검수

`references/qa.md` 순서대로. 특히
- `scripts/voice_check.py`로 자기 비판, 비공식 계산, 개발 문구 검사,
- `scripts/qa_all.mjs`로 모든 페이지 × (390, 1280) × (라이트, 다크),
- 무작위 10% 해설의 수치를 PDF와 재대조.

## 7단계. 넘겨주기

- README: 논문 추가 방법(카드 하나 추가 → 스크립트 → 커밋).
- GitHub Pages 설정 안내. 공개 전 교수님 확인 권장.

## 규모 감각 (첫 실전 기준)

- 해설 글 1편: 에이전트 1명, 7~10분, 약 17만~23만 토큰.
- 논문 카드 1편(추정): 해설의 1/4~1/3.
- 100편이면 카드에 약 15~25개 에이전트 배치, A 등급 15편 해설. 몇 시간 단위 작업이므로 체크포인트마다 사용자에게 보고한다.

## 첫 메시지에서 사용자에게 물을 것 (한 번에)

1. PDF 전달 방식(저장소 폴더/zip/업로드)과 논문 목록(CV, Scholar 링크).
2. 사이트 주인과 이름 표기(교수님 개인, 연구실), 공개 여부.
3. 빼야 할 논문, 꼭 강조할 논문.
4. 대규모 병렬(Workflow) 사용 허락과 대략의 규모.
5. 디자인 팩 선택은 철학 초안 확인 뒤에 따로 묻는다.
